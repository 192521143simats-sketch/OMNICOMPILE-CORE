# 1. What I understand you are actually trying to build

You are not trying to build just a compiler, a distributed computing application, a device-monitoring dashboard, or a website that assigns random tasks to connected computers.

You are trying to build a cross-platform, security-aware, fault-tolerant distributed compilation and computing system that uses heterogeneous devices to execute computational workloads intelligently.

The compiler is the primary purpose of the product. Distributed computing is the execution and resource-utilization architecture that extends the compiler beyond the machine on which it is running.

The system should accept source programs, process them through appropriate compiler pipelines, identify computational work that can be distributed safely, coordinate participating devices, execute eligible tasks across those devices, verify the returned results, recover from failures, and present the entire operation through a professional control interface.

In simple terms:

A user submits a program → the system compiles and analyzes it → eligible workloads are identified → the coordinator distributes suitable tasks to participating devices → devices execute those tasks → results are verified and consolidated → the system produces the final output and performance evidence.

This is the central identity of the product.

# 3. The central idea: One coordinator, heterogeneous workers

The architecture should be centralized for orchestration but distributed for execution.

This is an important architectural decision.

The Windows, Android and browser clients should not independently coordinate the network. They should communicate through one central coordinator.

The coordinator is responsible for deciding:

- Which jobs are accepted.
- Which tasks can be distributed.
- Which devices are eligible.
- Which device should receive each task.
- Whether a task has timed out.
- Whether a failed task can safely be reassigned.
- Whether returned results are valid.
- When the complete job can be marked successful.

The participating devices are execution resources, not independent administrators.

This gives the system a consistent control plane while allowing execution across different hardware and operating systems.

The network must work across different internet connections.

For example:

- The coordinator runs on a hosted server.
- A Windows worker connects from one home network.
- An Android worker connects using mobile data.
- A browser worker connects from a university network.

All should be able to participate without requiring a common Wi-Fi network, LAN discovery or inbound port forwarding on the worker devices.

The workers should establish outbound authenticated connections to the coordinator.

# 4. How the system must work — Complete operational lifecycle

This is the most important part of the product specification.

I would divide the system into ten interconnected operational stages.

## End-to-end system workflow

1. User submits source code

   The user uploads or pastes a C, Python or Java program, selects the language and submits it for processing.
2. Compiler analyzes the program

   The relevant language pipeline performs lexical analysis, parsing, semantic analysis and intermediate representation generation where supported.
3. Optimization and workload analysis

   The system performs applicable compiler optimizations and identifies computational operations that can be safely separated into independent tasks.
4. Task decomposition

   Eligible work is converted into bounded, identifiable tasks with defined inputs, requirements, execution limits and expected output formats.
5. Worker discovery and selection

   The coordinator evaluates registered workers and selects devices based on compatibility, availability, capacity, trust and resource conditions.
6. Secure task distribution

   The coordinator issues authorized tasks to selected workers through the common worker communication protocol.
7. Remote execution

   Windows, Android and browser workers execute compatible tasks within their respective execution environments.
8. Result validation

   The coordinator validates returned outputs, task identity, completion state, execution metadata and expected result structure.
9. Failure recovery and aggregation

   Failed or timed-out tasks are handled through safe retries or reassignment. Successful outputs are consolidated.
10. Final output and performance report

    The user receives the compilation result, execution status, relevant artifacts, errors and measurable system-performance information.

There is one important technical distinction: the compiler must not assume that every program can be distributed.

A normal sequential C program cannot automatically be divided into independent pieces and executed on arbitrary devices without considering data dependencies, shared state, side effects and execution order.

Therefore, the system must have a distribution eligibility and dependency analysis stage.

If a workload is not safely distributable, the compiler should process it locally rather than pretending that distributed execution occurred.

That distinction will make your project technically credible.

# 5. The compiler must remain the flagship component

The distributed platform should extend the compiler, not overshadow it.

Your system must genuinely perform compiler-related work rather than simply upload source code and send arbitrary calculations to connected devices.

## 5.1 Supported programming languages

| Language | Expected compiler responsibilities                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| C        | Lexical analysis, parsing, semantic validation, intermediate representation, optimization, code generation and executable generation. |
| Python   | Syntax validation, program analysis, supported optimization and execution through an appropriate runtime.                             |
| Java     | Syntax and semantic validation, supported optimization, bytecode generation and JVM-compatible execution.                             |

The implementation depth can differ between languages, but all three should have genuine processing pipelines.

For example, C can have a more explicitly developed compiler pipeline, while Python and Java can use their appropriate language toolchains and runtime infrastructure.

Do not force Python and Java through a C compiler pipeline.

## 5.2 C compilation pipeline

The C compiler should implement the following sequence:

| Stage                       | What it must accomplish                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Source input                | Accept C source code and validate the input.                                                                        |
| Lexical analysis            | Convert source code into tokens.                                                                                    |
| Syntax analysis             | Build and validate the program's syntactic structure.                                                               |
| Semantic analysis           | Identify type errors, undeclared identifiers and semantic inconsistencies.                                          |
| Intermediate representation | Convert the program into a structured representation suitable for further processing.                               |

## 5.3 Intermediate representation is particularly important

Your intermediate representation (IR) should act as a bridge between the compiler and distributed execution engine.

It should help the system:

- Represent program operations in a structured form.
- Identify dependencies between operations.
- Recognize independent computation regions.
- Determine which operations can be converted into distributed tasks.
- Preserve the relationship between task outputs and the original program.
- Support optimization before task execution.

This is one of the most important integration points between your Compiler Design and Software Engineering components.

## 5.4 What should actually be distributed?

I recommend three workload categories.

1. Independent computational workloads: Tasks that can execute independently, such as separate input batches or independent mathematical computations.
2. Data-parallel workloads: A supported computation divided into bounded data partitions, with each worker processing a different partition.
3. Compiler-generated eligible tasks: Computation units extracted from the supported intermediate representation and packaged with explicit dependencies and execution requirements.

The coordinator should not distribute the entire original source program indiscriminately to every worker.

Instead, it should distribute task packages.

A task package should contain:

- Unique task ID.
- Parent job ID.
- Task type and protocol version.
- Required execution capability.
- Input data or approved artifact reference.
- Execution constraints and resource limits.
- Task expiry and authorization information.
- Expected output structure.
- Integrity information.

This gives you a much more defensible distributed execution architecture.

## 6.3 Resource-aware scheduling

This should be one of the system's most important features.

The coordinator should not simply distribute tasks to whichever device connects first.

It should determine whether the device is appropriate for the workload.

For example:

- A computationally intensive task may require a Windows worker with sufficient available resources.
- A small portable task may be suitable for Android.
- A lightweight supported computation may be suitable for a browser.
- A device experiencing excessive thermal conditions should not receive additional work.
- An offline or unresponsive worker must not receive new tasks.

I would define worker eligibility using five principal dimensions:

1. Platform and task compatibility.
2. Available CPU and memory capacity.
3. Device health and execution constraints.
4. Network connectivity and responsiveness.
5. Worker authorization and trust status.

The scheduler should make its decision explainable. An administrator should be able to see why a device was selected or rejected.

## 6.4 Common Worker Protocol

All three worker types must communicate using a common, versioned protocol.

This is essential.

Windows, Android and Browser should not each have completely different task-management logic.

They should implement the same fundamental communication contract:

| Message       | Purpose                                  |
| ------------- | ---------------------------------------- |
| REGISTER      | Register a new worker.                   |
| HEARTBEAT     | Report that the worker remains active.   |
| CAPABILITIES  | Report supported execution capabilities. |
| TASK_ASSIGN   | Receive a task assignment.               |
| TASK_ACCEPT   | Confirm task acceptance.                 |
| TASK_PROGRESS | Report execution progress.               |
| TASK_RESULT   | Return task output.                      |
| TASK_FAILED   | Report execution failure.                |
| TASK_CANCEL   | Receive cancellation instructions.       |
| WORKER_PAUSE  | Pause new task acceptance.               |
| WORKER_LEAVE  | Gracefully leave the network.            |

HTTP and WebSockets are appropriate for the coordinator's API and live communication.

The protocol should also define message authentication, validation, version compatibility, timeouts and error handling.

# 7. Security must be part of the architecture, not a decorative feature

Your project title explicitly promises zero-trust and security awareness.

Therefore, security must affect how the system operates.

It should not be limited to a Security Dashboard showing a few green indicators.

I would expect the following.

## 7.1 Authentication and access control

- Secure administrator and user authentication.
- Role-based access control.
- Protected administrative operations.
- Secure session handling.
- Password hashing.
- Expiring enrollment invitations.
- Worker authorization before task assignment.

## 7.2 Worker trust

A connected device should not automatically be considered trustworthy just because it registered successfully.

The coordinator should validate:

- Worker identity and enrollment.
- Session authenticity.
- Protocol compatibility.
- Task authorization.
- Message integrity.
- Task completion and result consistency.

A worker can be registered but temporarily ineligible for execution.

That distinction is important.

## 7.3 Task security

Every distributed task should be:

- Authorized for the receiving worker.
- Bound to a specific task and job.
- Protected against unauthorized modification.
- Validated before execution.
- Restricted by execution and resource limits.
- Associated with an expiry or execution deadline.

## 7.4 Result integrity

A worker returning a successful response does not automatically prove that the computation is correct.

The coordinator must validate the result.

I would implement:

- Task ID and job ID matching.
- Input/output schema validation.
- Cryptographic hashes for artifact and payload integrity.
- Execution-state validation.
- Deterministic result comparison or recomputation for selected tasks.
- Detection of duplicate or stale responses.

An important qualification: hashes prove that data matches a particular digest; they do not prove that a worker performed the correct computation.

For stronger computational verification, selected deterministic tasks can be independently recomputed or executed redundantly and their outputs compared.

The system should distinguish integrity checking from computational correctness verification.

## 7.5 Execution isolation

The platform must never become an unrestricted remote code execution service.

The execution environment should enforce:

- Task allowlisting.
- Execution time limits.
- Memory/resource limits.
- Restricted filesystem access.
- Controlled input/output.
- Appropriate process isolation.
- Platform-specific execution restrictions.

Android should use its native application sandbox and approved bounded computation methods.

Windows execution should use an appropriately restricted environment.

Browser execution should remain within browser security boundaries.

# 8. Fault tolerance — The system must survive device failures

A distributed platform becomes meaningful when it can handle devices that disappear, fail or become unavailable.

Consider this situation:

There are four connected workers. The coordinator assigns tasks to all four. The Android device overheats and stops responding while one Windows worker loses its internet connection.

The system should not simply mark the entire job as failed.

It should:

1. Detect missing heartbeats or task timeouts.
2. Mark the affected workers as unavailable or degraded.
3. Identify their unfinished tasks.
4. Determine whether the tasks are safe to retry.
5. Reassign eligible tasks to other compatible workers.
6. Reject stale results from previous attempts.
7. Continue monitoring remaining tasks.
8. Consolidate successful results.
9. Report any unrecoverable tasks accurately.

# 10. The five metrics that must demonstrate that the system works

You previously wanted only a small number of meaningful performance metrics rather than a dashboard overloaded with numbers.

I agree. The following five should form the primary system-performance evaluation.

## Core system performance indicators

1\. Task Execution Success Rate

# — %

Percentage of assigned tasks that complete successfully and pass result validation.

\\[ \frac{\text{Validated successful tasks}}{\text{Total completed task attempts}}\times100 \\]

2\. Distributed Execution Performance

# — ms / s

Measures actual task execution time and compares eligible workloads against a local execution baseline.

\\[ \text{Speedup}=\frac{\text{Local execution time}}{\text{Distributed execution time}} \\]

3\. Resource Utilization Efficiency

# — %

Measures the actual CPU and memory utilization of participating workers while executing tasks.

4\. Fault Recovery Performance

# — s

Measures how long the system takes to detect a failed worker, reassign eligible tasks and resume progress.

5\. Result Integrity Rate

# — %

Measures the percentage of returned task results that pass the system's integrity and correctness-validation procedures.

These must be calculated from real execution records.

For a meaningful comparison, the system should run the same eligible workload locally and across distributed workers using comparable input data. It should also report network and coordination overhead.

A distributed execution that takes longer than local execution is not necessarily a failed experiment. It is valuable evidence about the conditions under which distribution is beneficial.

The application should never manufacture performance improvements to make the project look successful.

## Database responsibilities

MySQL should persist the information necessary to reconstruct system activity.

I would expect entities/tables covering:

- Users and roles.
- Worker registrations and capabilities.
- Enrollment invitations.
- Worker sessions and heartbeat records.
- Compilation jobs.
- Source/artifact metadata.
- Intermediate representation and compilation stages where persistence is required.
- Distributed jobs and task records.
- Task attempts and assignments.
- Task results and verification records.
- Security and audit events.
- Performance measurements.
- System configuration.

The database must distinguish a job from its individual tasks and distinguish a task from its individual execution attempts.

That is important for reliable retry management and historical analysis.

# 13. What the product must NOT become

I want to distinguish your intended product from several implementations that might superficially look similar but would weaken the project.

| Do not build                                                    | What you should build instead                                                        |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| A dashboard that only displays connected devices                | Actual device registration, task execution and lifecycle management.                 |
| A compiler interface that simply forwards everything to GCC     | A genuine compiler pipeline with analysis, IR, optimization and compilation outputs. |
| A system that distributes arbitrary source files to all devices | A dependency-aware, compatibility-checked task distribution engine.                  |
| A fake scheduler that assigns tasks randomly                    | An actual capability-aware resource scheduler.                                       |
| Android as a WebView wrapper                                    | A native Android execution worker.                                                   |
| A worker that only sends heartbeat messages                     | A worker that receives, executes and returns eligible tasks.                         |
| A security page with decorative indicators                      | Security checks that actually govern access and execution.                           |
| A recovery system that only changes a status label              | Real timeout detection, safe retry and task reassignment.                            |
| Artificial performance statistics                               | Measurements obtained from actual runs.                                              |
| A product dependent on the developer's laptop                   | An independently deployable coordinator and independently connecting workers.        |

There is another distinction worth making.

Zero-trust does not mean trusting nobody and refusing every device. It means that every device, session, task and result must be validated according to defined authorization and verification rules.

Similarly, fault tolerance does not mean that every possible failure can be recovered from. It means that the system identifies failures, applies appropriate recovery procedures and accurately reports unrecoverable conditions.

# 14. Development and deployment expectations

Your target is a near-industry-grade development and deployment experience, not necessarily a commercially published enterprise service.

I interpret that as the following requirements.

Development

- Modular TypeScript monorepo.
- Separate frontend, coordinator, compiler and worker modules.
- Versioned communication protocol.
- Consistent API contracts.
- Database migrations and persistent storage.
- Automated unit, integration and end-to-end tests.
- Structured application logging.
- Environment-based configuration.
- Reproducible builds.

Deployment

- Independently hosted coordinator.
- Persistent MySQL database.
- Containerized backend services.
- Kubernetes-based deployment as the intended hosting approach.
- HTTPS and secure WebSocket communication.
- Environment-specific secrets and configuration.
- Windows application packaging.
- Signed or otherwise controlled Android APK distribution.
- Browser worker accessible through the hosted website.
- Workers able to connect from different networks without requiring the developer's machine to remain online.

Docker remains useful for local development and building container images. Kubernetes is the intended deployment orchestration layer, rather than presenting Docker Compose as the final hosting architecture.

Testing

The system needs tests for:

1. Compiler correctness and generated artifacts.
2. Worker registration and protocol compatibility.
3. Task assignment and execution across all three platforms.
4. Authentication, authorization and task validation.
5. Worker disconnection, timeout and reassignment.
6. Result integrity and aggregation.
7. Resource monitoring and scheduling decisions.
8. Performance comparison between local and distributed execution.

A particularly important acceptance condition is that the Android and Windows workers must be tested as actual independently running applications, not merely as development simulations.

# 15. What I would prioritize to make this a successful product

There is a risk in a project of this size: trying to implement every advanced capability simultaneously can result in many partially working modules.

I would divide the final implementation into four levels.

| Level                         | Priority  | What must be delivered                                                                                             |
| ----------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------ |
| 1. Core functionality         | Essential | Compiler pipelines, coordinator, MySQL, job/task lifecycle and actual execution.                                   |
| 2. Cross-platform integration | Essential | Working Windows, Android APK and browser workers using a common protocol.                                          |
| 3. Reliability and security   | Essential | Authentication, worker authorization, result validation, resource-aware scheduling, fault recovery and audit logs. |
| 4. Evaluation and deployment  | Essential | Kubernetes deployment, automated testing, real performance measurements, reporting and reproducible builds.        |

I would not treat the last three levels as optional enhancements. They are part of the promised product.

Advanced features such as predictive scheduling, machine-learning-based resource allocation, sophisticated compiler optimizations and additional hardware backends can remain future extensions.

# 17. My final understanding of your expectations

I want to emphasize five things that I believe define your project.

1\. It must be a real compiler product.

The compiler must accept source code, process it through genuine language-specific pipelines, perform optimization and generate appropriate outputs. Distributed execution must be connected to this compiler functionality.

2\. It must demonstrate genuine heterogeneous computing.

A Windows computer, an Android phone and a browser must be able to independently join the same computing network and perform actual supported work. They must not be simulated versions of one another.

3\. It must be intelligent in its resource management, without requiring AI.

The platform should make rule-based, capability-aware decisions about task placement, device availability, execution compatibility and recovery. It should behave intelligently through deterministic algorithms and measurable system logic.

4\. It must be secure and resilient by design.

Untrusted workers, unauthorized tasks, invalid results, disconnected devices and execution failures must be handled through actual mechanisms, not just displayed as dashboard notifications.

5\. It must be demonstrable, measurable and independently deployable.

You should be able to start the central platform, connect devices from different networks, compile a program, distribute eligible workloads, observe actual execution, disconnect a device, recover tasks and produce measurable performance evidence.

## The one-sentence product definition

## OmniCompile Core

A security-aware, fault-tolerant distributed compiler platform that transforms supported source programs into optimized execution workloads, intelligently orchestrates eligible computations across heterogeneous Windows, Android and browser devices, verifies execution results, and provides reliable, measurable and centrally managed compilation and distributed computing.

## One final architectural distinction I would preserve

I would make sure the project is built around this hierarchy:

- Compiler = Intelligence: Understands, analyzes, optimizes and prepares programs.
- Coordinator = Control: Manages the entire computing network.
- Scheduler = Decision-making: Determines where eligible work should execute.
- Workers = Execution: Perform the assigned computation.
- Security and verification = Assurance: Establishes whether operations and results are authorized and valid.
- Fault recovery = Resilience: Keeps eligible workloads progressing when devices fail.
- Dashboard = Visibility and control: Lets users understand and manage the complete system.

That is the product I believe you have been working towards, rather than two university projects joined together.

My strongest recommendation is to preserve this architecture and resist expanding the scope with unrelated features. Make the compiler-to-distributed-execution connection exceptionally solid. A working three-platform execution network with a genuine compiler, secure task distribution, verifiable results and demonstrated failure recovery is already a substantial and technically meaningful software engineering product.
